## How to read this document

### Evidence labels

- **observed** — the surface, label or vocabulary was seen in the authenticated session or the public-page captures. A label is not behavior.
- **partly observed** — a label, control, column set, audited entity or endpoint appears in the evidence, but the workflow's behavior, guards, persistence or outcome was not exercised.
- **unobserved** — neither surface nor vocabulary was seen. An unavailable feature is an explicit unknown, not proof of absence.

### Two claims that are never merged

1. An **observed label** is configuration text seen in the incumbent's interface. It establishes that the incumbent names a state. It does not establish permitted transitions, guards, audit effects or enforcement.
2. A **designed** state, transition or permission is our proposal, owned by the named task. No transition in this document was executed or observed in the incumbent, and nothing here claims enforcement.

Every state transition set in Part 2 is designed. Part 2's Source column records, per row, whether the state name itself was observed as a label.

### Rows without a complete owner

These are gaps in the plan set, not decisions deferred by a plan. They are recorded here because the roadmap's P2 gate requires the state and role contracts, and each of these rows currently has no task that would produce one.

1. **Check-out and visit-level billing completion.** The incumbent exposes `Mark as Checked-Out` and `Mark as Billed` labels. Our attendance model has no departure kind, and no task defines a visit-level fact answering "arrived, treated, not yet billed". clinical T5 closes the encounter; nothing closes the visit.
2. **Reporting definitions.** CAPABILITIES requires analytics where every metric declares a numerator, denominator, time basis, filters and freshness. billing T9 authorizes five report scopes and guards queries; no task defines a report, a projection or its freshness contract.
3. **Audit search and review.** foundation T4 owns audited command recording and protected access; no task specifies search by actor, record class, action and time range, or the historical-activity behavior the incumbent exposes.
4. **User lifecycle and access review.** foundation T2 is designed to enforce membership and revocation; no task defines invitation, role assignment, ownership transfer, periodic access review or the review record the capability matrix requires.
5. **Practice setup.** Organization, location, provider directory and procedure catalog are prerequisites for almost every other row and have no owning task. scheduling T7 owns resources and hours, billing T9 owns fee schedules, clinical T9 owns note templates.
6. **Prescribing.** The capability matrix marks it an integration gate; no plan or task owns the workflow, the partner decision or the prescriber-identity requirements.

## Part 2 — State matrix

Every transition set below is designed. No transition was executed or observed in the incumbent, and none is claimed as enforced. The Source column states whether the state name was observed as a label or is ours.

Two conventions apply throughout. Terminal means the record is not deleted and no further transition is defined; corrections are new records. Irreversible refers to content: a frozen or posted record is not edited by anyone, and the correction path is named in the row.

Three observed labels are not states and appear at the end of the appointment rows: `Mark as Treatment Complete` and `Mark as Billed` are separate facts in our model, and `ASAP` is a priority flag.

## Part 3 — Role matrix

### The observed configuration, stated once

The incumbent exposes an access-control matrix with three columns: Category, Resource and Access. The observed categories are `Financial`, `Report` and `Setup`. **Every observed row had Access set to `All Users`**, including the ledger, receivables, undistributed payment amounts, open-claims management and clinic setup. Access levels themselves, meaning whether the column selects a group, a role or a per-user list, were not enumerated, and server-side enforcement was not tested.

Two conclusions stay separate. The vendor supports per-resource control at report granularity. This clinic's configuration grants everything to everyone. The second is an operational finding about one practice, not a claim about the vendor's defaults.

The nine roles below are our design. The incumbent's matrix has no role column, so this role set is not derived from it.

### Roles

| Role | Default posture | What the role exists for | Notes |
|---|---|---|---|
| Front desk | Narrow, patient-facing operations | Identity capture, scheduling, arrival, payment intake, statement print, recall and waitlist contact | The broadest set of patient-facing writes and the narrowest set of aggregate reads. Financial execution beyond taking a payment belongs to billing. |
| Scheduling coordinator | Narrow, schedule-focused | Requests, availability, booking, reschedule, cancellation, waitlist, recall | No clinical content, no ledger, no setup. |
| Dental assistant | Visit support | Arrival, seating, imaging capture and association, lab slips, chart support under a clinician | No signing, no financial execution, no schedule ownership. |
| Hygienist | Clinical authorship within own encounters | Chart, periodontal, history, hygiene notes, recall interval recommendation | Signing and amendment only where the tenant configures it and only for encounters the hygienist authored, which is a conditional grant, not a default. |
| Treating dentist | Clinical authority | Diagnosis, chart, treatment planning, estimates, consent attestation, note signing and amendment, own clinical reads | No ledger, no claim submission, no access administration. |

### What the incumbent's single configuration tells us

The observed configuration is the concrete failure this matrix is written against. A per-resource permission system that supports report-level granularity but is configured `All Users` delivers no least privilege at all. The controls exist, the practice chose openness, and nothing visible records that choice as a risk. Our readiness gates therefore require default-deny, a stated reason for every allow, and evidence that the allow was not achieved by hiding a control.

None of the defaults in this part has been implemented, and none is a claim that the incumbent denies anything.

## What a negative test must prove for each row

Two rules govern every row in Parts 1 to 3.

**Every allow implies at least one negative case.** An allow that has no matching refusal case is an untested permission, not a granted one. The negative case must name a principal who should be refused and assert four things: the operation is refused; the refusal shape is the same as for a record that does not exist, so existence does not leak; no side effect occurs in the database, the outbox, storage or an external provider; and exactly one denial is audited with the actor, operation, resource class and outcome. Where the operation crosses a boundary, the refusal case must also cover the cross-tenant variant, the revoked-membership variant, the downgraded-role variant with an unexpired token, and the expired relationship or grant variant.

**Every deny must be tested from both the UI and the API.** A hidden button, a disabled control or a missing menu entry is not enforcement, and it is not the test. The API attempt is made with a valid session so that the refusal is authorization and not authentication, and it confirms that the deny is applied before data is fetched rather than by filtering rows after a successful read. A deny that returns a different count, timing or error shape when records exist is a leak. Where the plan claims parity, the same deny is asserted through MCP and through a worker job with the same typed error code.

| Row group | Negative case that must exist for each allowed cell | Assertions |
|---|---|---|
| Financial reads (AR, ledger, KPI, statement) | A role with patient read but without the specific financial scope; a colleague in the same role but another location | Identical denial whether or not records exist; no totals or counts inferable from a filter or a count; the read that is allowed is itself audited |
| Financial writes (ledger postings, allocations, refunds, statements generate, plans) | The same role without the execution scope; a second actor where approval is required; a replayed idempotency key with a different payload | One committed result per key; a duplicate provider receipt creates no second entry; a reversal cites its original; a denied actor leaves no partial journal, audit or outbox row |
| Report classes | A user holding several report scopes but not this one; a service account without the scope | Refusal is not a shortened report and not a zero total; an unreconcilable report states the discrepancy instead of truncating; distribution totals reconcile to the journal or the difference is named |
| Open claims and undistributed funds | A billing user without the undistributed scope attempting allocation; a clinician attempting reassignment | No inferred total through filtering; reassignment retains prior assignment history; no claim or allocation is orphaned by a departure |
| Setup | A non-administrator attempting a configuration change; an administrator attempting to change another tenant's configuration | Configuration change is audited with before and after references; a disabled location alters no history; a resource label matching a state vocabulary is refused |
| Clinical read and clinical sign | A clinician with patient read but not the signing scope; a hygienist signing another clinician's note; the same note amended without oversight scope | Signed content is unaltered by any refused attempt, including a direct table write under the application role; the digest still verifies; exactly one conflict for concurrent signatures |
| Scheduling writes | A location-restricted user booking at another location; a concurrent booking on the same constrained resource | Exactly one booking and one conflict; the conflict names the blocking resource; no second appointment row and no success audit |

| Administrative and audit surfaces | A practice administrator attempting a clinical signature they are not credentialed for; a non-administrator attempting user or role changes | Access administration is audited including the read of audit itself; a revoked principal cannot continue a privileged job or download a cached export |

## What this matrix does not establish

- No transition, guard, role or permission in this document was executed, observed or tested. The incumbent's transitions, guards, role enforcement and error semantics remain unobserved.
- A label is not a rule. The observed status list, worklists, report names and access rows establish vocabulary and surface shape only.
- Plan ownership is a proposal, not a commitment. The nine workstream plans are planning proposals and nothing here authorizes implementation.
- The gap list at the end of Part 1 is not a decision record. Each gap needs an owning task before the P2 exit condition in [ROADMAP.md](ROADMAP.md) can be claimed.
- Passing tests against synthetic data would not establish clinical safety, financial correctness against a payer, or production readiness.
