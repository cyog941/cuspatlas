# ADR 0004: Device bridge boundary (I6, server side)

Status: **recommended-pending-approval**, 2026-11-12. Evidence category: proposed (decisions) and configured and tested on synthetic data only (`tests/integration/imaging-bridge.test.ts`, `tests/integration/imaging-offline.test.ts`). No device, sensor SDK, acquisition software or bridge is qualified: I-S1 (hardware matrix) and I-S3 (where acquisition runs) remain **blocked-on-discovery**, and the native bridge (a separately reviewed companion) is **not built**. Nothing here claims device support, acquisition, compatibility or safety. Reviewers required before release: security review, an operator for I-D2/I-D7, and the I-S1 pilot practice.

## Decision

The server exposes narrow, typed bridge contracts; a future reviewed bridge calls them. A test-only synthetic bridge client (`tests/integration/support/synthetic-bridge.ts`) exercises them.

| # | Question | Implemented as (pending approval) |
|---|---|---|
| 1 | Who is a bridge? | Its own principal kind `device`: a `principals` row (kind `device`) plus an `imaging_devices` row in one tenant. The database refuses a staff membership for it; `authorize` never admits it; the tenant transaction rechecks the live device row (pending only for pairing) instead of a membership. |
| 2 | How does it pair? | A human administrator (`admin.configure`) registers the device with its allowlist (pending) and issues a one-time code (`cpb1.<tenant>.<device>.<pairing>.<secret>`, default 10 min, at most 1 h, shown once, SHA-256 stored, superseded by a newer code, single use). The bridge sends the code, a new Ed25519 public key and a proof of possession (signature over `cuspatlas-bridge-pair:v1:<pairing>:<publicKey>`). Every failure is the same 401; the attempt row names the reason with no tenant or actor. |
| 3 | How does it authenticate afterwards? | A device assertion per request: compact JWS (EdDSA, `typ cuspatlas-device-assertion+jws`, `kid <device>.<keyVersion>`) signed by the device's active key, with `iss = sub = device`, `aud urn:cuspatlas:bridge:v1`, `tid` (must equal the stored tenant), a lifetime of at most 120 s, a single-use `jti` (consumed in its own committed transaction), `htm`/`htu` binding it to one request and, for every request with a body, `bdy` (base64url SHA-256 of the exact body bytes, checked before the body is parsed, so a body cannot be swapped under a valid assertion). Staff tokens never verify as device assertions and device assertions never verify against the staff issuer key, so each is 401 on the other's routes. Private keys never reach the server. |
| 4 | Jobs | Typed kinds `acquire`, `import`, `probe` with a relative `scopePath` (data the bridge resolves inside its own import root). Enqueue checks the device state, the kind allowlist and the path rules; claim rechecks the current allowlist (database function `imaging_bridge_job_allowed`, also a trigger) and denies a job the allowlist no longer admits. A claimed job is a server-signed envelope (EdDSA, `typ cuspatlas-bridge-job+jws`) carrying the job, device, tenant, kind, path, claim nonce, attempt and expiry; the bridge verifies it with the server key it learned at pairing. |
| 5 | Results | A device-signed result (`typ cuspatlas-bridge-result+jws`) names the job, device, claim nonce, attempt, outcome and the artifact's media type, length and SHA-256. The server verifies the signature with the current key, freshness (300 s), nonce and attempt, and that the signed digest equals the staged bytes; then the I2 gates run and the object is created or deduplicated with `bridgeImport` provenance. A result for a completed job is a recorded duplicate (409 `replayed_result`), never a second object. |
| 6 | Paths | Accepted: relative segments of `[A-Za-z0-9._-]` joined by `/`, at most 240 characters, NFC, no `.`/`..` segment. Refused (422 `path_traversal`): absolute, drive, backslash, control characters, empty segments, traversal. Outside every allowed prefix (segment-wise, never by substring): 409 `path_outside_import_root`. The same rule is a database CHECK. The application never receives a filesystem path, shell or device handle. |
| 7 | Revocation and rotation | Revocation is final: keys revoked, every open job (including one already claimed) denied, staged bytes discarded. Rotation is the device's own act: asserted with the current key, proven by the new key; the old key stops working for assertions and results at once. |
| 8 | Updates (I-D7) | Contract only: `verifyUpdateManifest` accepts a manifest JWS (`typ cuspatlas-bridge-update+jws`) from a pinned trust set, refusing unsigned/`none`, untrusted keys, bad signatures, malformed or expired manifests, downgrades (version not newer) and artifact digest mismatches. No installer, channel or release key exists. |
| 9 | Transport | Bridge routes are REST only under `/v1/bridge/*` (`security: deviceAssertion`), never MCP tools; staff administration (register, pairing code, allowlist, revoke, enqueue, reads) is REST and MCP. |

## Review hardening (I5-I9 independent review)

- Anonymous `POST /v1/bridge/pair` is throttled in memory before any database work: 5 failures per pairing code and 30 per source per minute, then 429 `rate_limited` (no attempt row for a throttled request). A multi-instance deployment adds an edge limit (deployment decision).
- Path prefixes compare literally at the database (`left(path, length(prefix)+1) = prefix || '/'`), not by `LIKE`.
- A device row may only name a principal of kind `device` (insert policy); expired assertion identifiers (over an hour past expiry) are purged by the reconcile sweep; a pending device is refused as `device_unpaired`.

## Open (blocked)

Vendor SDKs, capture software, watched-folder conventions, operator steps and fallbacks (I-S1, I-S3); the bridge's own storage of its private key, its import-root configuration and its update channel (I-D7); production signing-key custody (`CUSPATLAS_BRIDGE_SIGNING_KEY_PEM`, Ed25519 PKCS8; absent outside synthetic-test means claims are a typed 503 with alert `imaging_bridge_signing_key_missing`).
