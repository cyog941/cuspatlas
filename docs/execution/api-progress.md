### A4: operation catalog

- `packages/contracts/src/catalog/operations.json` is generated by `scripts/catalog/build-catalog.ts`
  from `ACTION_POLICIES`, the route manifests, the MCP tool table and the worker's literal
  `authorize` calls (`pnpm catalog:generate`); `pnpm catalog:check` (inside `contract:check` and `ci`)
  fails when the committed catalog is stale. 355 operations at this head.
- Each entry: operation id, owner workstream, kind, authorization path, policy action, scope,
  principal kinds, transports (rest/mcp/portal/bridge/worker), REST method/path/schema refs, MCP tool,
  refusal statuses, idempotency, sensitivity (none/operational/phi/phiBulk) and status.
- Authorization paths are recorded honestly: staff REST, MCP and worker operations go through
  `authorize` (ACTION_POLICIES); portal operations through the S5 relationship policy; bridge
  operations through the live device row and allowlist; pairing through the one-time code; health is
  public; five actions are capability-only checks inside another operation. The catalog does not
  claim `authorize` covers portal or device calls.
- Runtime proof: on the real app under the runtime role, every staff REST route (with a scope) called
  by an active member with no scope loads the live membership twice (authentication, then
  `authorize`) and records a `scope_missing` (or `principal_kind_denied` for service-only operations)
  security attempt naming the operation.
- Derived (declared, not independently proven by the catalog): `kind` (GET, read-only MCP tool or a
  read-named POST is a query) and `idempotency` (commands require a key except imaging `unkeyed`
  grants). Per-workstream idempotency suites remain the evidence for the latter.
- Registry reconciliation: `syntheticTasks.read|write|approve` and `outbox.deliver` were used by the
  policy table but missing from SHARED-CONTRACTS; recorded there as F foundation scopes.

### A3: scope registry and the new-operation procedure

- `packages/contracts/src/catalog/scopes.json` and `docs/api/scopes.md` are generated from the catalog
  (38 staff scopes at this head) and checked against the human registry in SHARED-CONTRACTS. Every
  scope the policy table uses is registered; `claims.read` is registered but unused and is reported as
  a reviewed orphan (a new orphan fails). Relationship scopes are the five S5 names, never staff scopes.
- Scope-name lint: `noun.verb` with exactly one dot; a dotless camel-case name (`receivablesRead`) is
  rejected with the correct form, as are wildcards, prefix wildcards, empty and upper-case names.
- `docs/api/new-operation.md` publishes the five steps (`catalog`, `scope`, `policy`, `harness`,
  `openapi`); the checklist test runs them over every catalog operation and over a synthetic new
  operation that skipped steps. "Harness" is evidence by name (operation id, tool name or REST path
  in a workstream harness or fixture), on top of the derived A7 matrix; it is not proof that the
  harness covers every negative class.
- Not done: there is no grant API for staff scopes, so "a human-only scope cannot be granted to an
  agent" is proven only as "can never be exercised by one" (A7). Default role grants remain A-D2.

### A1: contract pipeline, generated client and shared-representation conformance

- ADR `docs/adr/0007-contract-pipeline.md` records the pipeline: code tables and JSON Schemas are the
  sources; one generator (`pnpm catalog:generate`) derives every artifact and writes nothing when
  validation fails; `catalog:check` rejects any stale or hand-edited generated file.
- OpenAPI is conformance-checked, not regenerated wholesale in this batch: the documented operations
  (method, path, operationId) equal the catalog REST operations exactly, on top of the existing
  contract drift check. Replacing the per-workstream OpenAPI generators remains open.
- Shared representations: no tenant field, bare `<entity>Id`, scalar money or zoneless `*At`
  timestamp in any schema definition reachable from an operation; request objects are closed. The
  only defects in unreachable definitions are the four scalar minor-unit amounts of the fake
  clearinghouse `RemittanceAdvice` (adapter-internal), listed explicitly. Allowed `...Id` fields that
  are not entity references: `correlationId`, `providerEventId`, `jobSigningKeyId`.
- `packages/client`: `src/generated.ts` (types from the JSON Schemas plus one typed entry per REST
  operation, 348 entries) and a hand-written transport (`src/index.ts`) with no business logic; a
  refusal is never `ok`. The test calls the real app: create, read, a 404 refusal, and a smuggled
  `tenantId` property rejected with 400 (not stripped). The two OpenAPI-local result schemas (Health,
  Session) are typed `unknown`.

### A5: change control, deprecation and the sunset record

- `packages/contracts/src/catalog/baseline.json` is the committed, versioned contract snapshot (per
  operation: transports, scope, principal kinds, REST method/path, MCP tool and a normalized,
  $ref-resolved request-schema summary). `classifyChange` reports additive and breaking changes with
  the field path: removed or renamed operation, dropped transport or principal, changed scope, new
  required property, removed property of a closed object, narrowed enum, tighter max/min, changed
  pattern, nullable made non-null. A baseline that cannot be ordered stops the pipeline.
- The gate (`catalog:generate` and the test) refuses a breaking change unless the operation has an
  entry in `deprecations.json` whose sunset date has passed; removing before the sunset is refused.
- Deprecated operations still answer and audit. REST responses (success and refusal) carry
  `Deprecation: @<epoch>` (RFC 9745), `Sunset` (RFC 8594) and a `Link` to the register; MCP tool
  descriptions and every result (`_meta.deprecation`) carry the notice. Proven with a synthetic test
  entry injected through `AppDeps.deprecations` / `McpServerDeps.deprecations`; the published list is
  empty, so no operation is deprecated at this head.
- `docs/api/sunset-register.md` is generated from the entries and checked against the catalog.
- Open: the deprecation window length (A-D1) is a human decision; no default is asserted.

### A6: MCP parity from the catalog

- The tool list is asserted equal to the catalog (not regenerated from it: tool handlers stay in the
  per-workstream tables). `toolCatalogDrift` (apps/mcp/src/catalog.ts) runs in `buildMcpServer`: a
  hand-added, off-catalog, remapped, duplicate or non-staff tool, a read-only hint that contradicts
  the catalog kind, or a missing catalog tool refuses startup. 326 tools at this head.
- `tools/list` through the real transport equals the catalog MCP operations with matching read-only
  hints. One matrix over all workstreams (B 64, C 88, E 58, F 12, I 54, S 79 operations) checks REST
  registration, MCP listing, policy, OpenAPI and harness rows for every operation; the five
  per-workstream matrices (S17, C18, E9, I9, B10) keep their specific assertions unchanged.
- The same command through REST and MCP (`patients.create`) yields the same result shape and version;
  a REST-audience credential is refused by the MCP transport before any tool runs. Identical refusals
  per operation are proven by the A7 matrix.
- `docs/api/mcp-surface.md` lists the REST-only operations and the candidate disable list (A-D3, open).
