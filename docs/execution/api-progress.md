### A4: operation catalog

- `packages/contracts/src/catalog/operations.json` is generated by `scripts/catalog/build-catalog.ts`
  from `ACTION_POLICIES`, the route manifests, the MCP tool table and the worker's literal
  `authorize` calls (`pnpm catalog:generate`); `pnpm catalog:check` (inside `contract:check` and `ci`)
  fails when the committed catalog is stale. 355 operations at this head.
- Each entry: operation id, owner workstream, kind, authorization path, policy action, scope,
  principal kinds, transports (rest/mcp/portal/bridge/worker), REST method/path/schema refs, MCP tool,
  refusal statuses, idempotency, sensitivity (none/operational/phi/phiBulk) and status.
- Authorization paths are recorded honestly: staff REST, MCP and worker operations go through
  `authorize` (ACTION_POLICIES); portal operations through the S5 relationship policy; bridge
  operations through the live device row and allowlist; pairing through the one-time code; health is
  public; five actions are capability-only checks inside another operation. The catalog does not
  claim `authorize` covers portal or device calls.
- Runtime proof: on the real app under the runtime role, every staff REST route (with a scope) called
  by an active member with no scope loads the live membership twice (authentication, then
  `authorize`) and records a `scope_missing` (or `principal_kind_denied` for service-only operations)
  security attempt naming the operation.
- Derived (declared, not independently proven by the catalog): `kind` (GET, read-only MCP tool or a
  read-named POST is a query) and `idempotency` (commands require a key except imaging `unkeyed`
  grants). Per-workstream idempotency suites remain the evidence for the latter.
- Registry reconciliation: `syntheticTasks.read|write|approve` and `outbox.deliver` were used by the
  policy table but missing from SHARED-CONTRACTS; recorded there as F foundation scopes.

### A3: scope registry and the new-operation procedure

- `packages/contracts/src/catalog/scopes.json` and `docs/api/scopes.md` are generated from the catalog
  (38 staff scopes at this head) and checked against the human registry in SHARED-CONTRACTS. Every
  scope the policy table uses is registered; `claims.read` is registered but unused and is reported as
  a reviewed orphan (a new orphan fails). Relationship scopes are the five S5 names, never staff scopes.
- Scope-name lint: `noun.verb` with exactly one dot; a dotless camel-case name (`receivablesRead`) is
  rejected with the correct form, as are wildcards, prefix wildcards, empty and upper-case names.
- `docs/api/new-operation.md` publishes the five steps (`catalog`, `scope`, `policy`, `harness`,
  `openapi`); the checklist test runs them over every catalog operation and over a synthetic new
  operation that skipped steps. "Harness" is evidence by name (operation id, tool name or REST path
  in a workstream harness or fixture), on top of the derived A7 matrix; it is not proof that the
  harness covers every negative class.
- Not done: there is no grant API for staff scopes, so "a human-only scope cannot be granted to an
  agent" is proven only as "can never be exercised by one" (A7). Default role grants remain A-D2.

### A1: contract pipeline, generated client and shared-representation conformance

- ADR `docs/adr/0007-contract-pipeline.md` records the pipeline: code tables and JSON Schemas are the
  sources; one generator (`pnpm catalog:generate`) derives every artifact and writes nothing when
  validation fails; `catalog:check` rejects any stale or hand-edited generated file.
- OpenAPI is conformance-checked, not regenerated wholesale in this batch: the documented operations
  (method, path, operationId) equal the catalog REST operations exactly, on top of the existing
  contract drift check. Replacing the per-workstream OpenAPI generators remains open.
- Shared representations: no tenant field, bare `<entity>Id`, scalar money or zoneless `*At`
  timestamp in any schema definition reachable from an operation; request objects are closed. The
  only defects in unreachable definitions are the four scalar minor-unit amounts of the fake
  clearinghouse `RemittanceAdvice` (adapter-internal), listed explicitly. Allowed `...Id` fields that
  are not entity references: `correlationId`, `providerEventId`, `jobSigningKeyId`.
- `packages/client`: `src/generated.ts` (types from the JSON Schemas plus one typed entry per REST
  operation, 348 entries) and a hand-written transport (`src/index.ts`) with no business logic; a
  refusal is never `ok`. The test calls the real app: create, read, a 404 refusal, and a smuggled
  `tenantId` property rejected with 400 (not stripped). The two OpenAPI-local result schemas (Health,
  Session) are typed `unknown`.

### A5: change control, deprecation and the sunset record

- `packages/contracts/src/catalog/baseline.json` is the committed, versioned contract snapshot (per
  operation: transports, scope, principal kinds, REST method/path, MCP tool and a normalized,
  $ref-resolved request-schema summary). `classifyChange` reports additive and breaking changes with
  the field path: removed or renamed operation, dropped transport or principal, changed scope, new
  required property, removed property of a closed object, narrowed enum, tighter max/min, changed
  pattern, nullable made non-null. A baseline that cannot be ordered stops the pipeline.
- The gate (`catalog:generate` and the test) refuses a breaking change unless the operation has an
  entry in `deprecations.json` whose sunset date has passed; removing before the sunset is refused.
- Deprecated operations still answer and audit. REST responses (success and refusal) carry
  `Deprecation: @<epoch>` (RFC 9745), `Sunset` (RFC 8594) and a `Link` to the register; MCP tool
  descriptions and every result (`_meta.deprecation`) carry the notice. Proven with a synthetic test
  entry injected through `AppDeps.deprecations` / `McpServerDeps.deprecations`; the published list is
  empty, so no operation is deprecated at this head.
- `docs/api/sunset-register.md` is generated from the entries and checked against the catalog.
- Open: the deprecation window length (A-D1) is a human decision; no default is asserted.

### A7: forbidden-operation matrix

- Derived from the catalog: 2082 cases over 354 operations (every operation except public health),
  by principal kind human 1030, service 360, portal 351, device 341; fingerprints per surface REST
  1970, MCP 974, portal 52, bridge 18, worker 42. Runs on the real app and MCP server under the
  runtime role in about 80 s on this host.
- Every staff operation: excluded kind with full scopes is `principal_kind_denied`, admitted kind
  without scope is `scope_missing`, identical on REST and MCP (outcome, code and internal reason);
  revoked membership; token naming another tenant; portal and device identities on the staff
  transport. Portal, bridge/pairing, worker and capability operations have their own cases.
- First run (red, exit 1, 3 failed / 4 passed) found: a too-broad agent-boundary rule
  (`billing.plans.amend` is a payment-plan amendment, not clinical), the MCP transport refusing
  revoked or unscoped credentials before tool dispatch (now recorded as a transport denial), and one
  reason difference: `syntheticTasks.proposals.approve` for a service principal is denied as not-found
  because the proposal is loaded before the policy check; reviewed and listed (still denied, REST =
  MCP; existing-proposal refusals are in proposal-policy.test.ts). No operation was allowed that the
  catalog forbids.
- Not covered by this matrix: record-level cross-tenant cases on existing records, locations,
  relationship expiry and queued-job revocation stay in the workstream harnesses; there is no UI path
  yet (UI deferred).

## Hardening H1 (review fixes, 2026-11-05)

- A-M1 change control: the gate compares against the baseline and deprecations committed at the base (`CUSPATLAS_CATALOG_BASE_REF`, else the merge base with `origin/main`, else the committed `HEAD~` when no remote ref exists). A missing or corrupt working-tree baseline is fatal unless `--first-publication` is passed explicitly; a breaking change needs a base deprecation entry with `announced < sunset`, a window of at least 90 days (`CUSPATLAS_DEPRECATION_WINDOW_DAYS`; A-D1 still pending) and a passed sunset. A base that predates the catalog (today's `origin/main`) has nothing published, so the gate is dormant until the baseline lands there. Tests: `tests/integration/api-change-control-gate.test.ts`.
- A-M2/A-S8: SHARED-CONTRACTS now has a "Scope registry table"; generation reads only its rows, and its `Human only` column is the published `humanOnly` flag. The forbidden matrix asserts every human-only-scope operation admits no service, portal or device principal (no hand list).
- A-D4 (recommended-pending-approval): grey-zone agent operations follow the AI default (read/draft only; anything that changes access, consent, money responsibility or configuration is human). No proposal/approval flow exists for these operations, so they are human only: `portal.principals.enroll`/`.revoke`, `communications.consents.record`/`.optOut`, `patients.relationships.add`/`.revoke`, `billing.plans.authorize`/`.autopay`, `billing.responsibility.transfer`, `scheduling.locations.changeTimeZone`, `scheduling.resources.define`, `imaging.objects.content`, `imaging.objects.grantRead`, and the admin `imaging.storage.reconcile`. - A-S8: `admin.configure` operations are `operational` sensitivity, any `.export`/`.export.*` (including `imaging.export.blobs`) is `phiBulk`; `imaging.objects.revokeGrant` requires `imaging.write`.

## A20/B11 (operational read models: list envelope, vocabularies, claims queues)

- A20 step 1 (red): `tests/integration/list-catalog-conformance.test.ts`. Classification rule: a catalog operation is a **list** when its kind is `query` and either (a) its REST success schema's `data` is exactly `type: 'array'` (a union such as the generic `EngagementRead` does not count), or (b) the last segment of its operation id is `list*`, `search`, `worklist`, `find`, `enrollments`, `daily` or ends in `List`. The rule classifies 57 operations. Red against b6e8c59: 57 unregistered, 52 without the envelope (only S availability/presence/staging and the E10 thread list carried it; `syntheticTasks.list` was unresolvable because its schema ref has no prefix), 5 schema files without the canonical `$defs`.
- A20 step 2 (green): the envelope is attached by the transports from one table, `LIST_OPERATIONS` in `packages/contracts/src/list-operations.ts` (57 entries: ordering key/direction/tie-break as each domain read's ORDER BY, limit default/max or `'parent'`, cursor, scope rule, exact `total` or capped `lowerBound` field, `sensitiveFilters`). REST: `apps/api/src/list-envelope-hook.ts` (onRoute wraps the handler in a list scope; preSerialization adds top-level `envelope`). MCP: `callTool` in `apps/mcp/src/server.ts`. The four lists whose domain already builds the envelope (S availability/presence/staging, E10 threads) are `placement: 'existing'`. Scope comes from the live authorization decision: `authorize` records the membership restriction into an AsyncLocalStorage list scope (`packages/domain/src/policy/list-scope.ts`); `scope: 'location'` lists report `assigned_locations` for a restricted caller or `location_set` for an explicit `locationRef` filter, `'tenant'` lists (patient/parent-bounded, not location-filtered) report `tenant_wide`. Truncation: a cursor or a domain `truncated` flag, or a full page of a capped read without a cursor (`count.atLeast`); otherwise `count.exact`. Patient search reports `name`/`birthDate`/`phone` filters as `provided` (never echoed). The seven generic engagement lists moved from `EngagementRead` to `EngagementListRead` (same data plus required envelope; catalog/OpenAPI updated). Retrofit landed as one commit across S, C, B, E, I, M because the mechanism is shared (deviation from the per-workstream commits). Tests: `list-catalog-conformance` (catalog-wide), `list-envelope-behaviour` (empty, truncated, location-restricted, explicit location set, REST/MCP parity).
- Open (A20): capped reads without a cursor that return exactly a full page report `truncated`/`atLeast` conservatively (domain reads fetching limit+1 would make this exact); work-item lists' `count` is capped by their SQL LIMIT so it is used only as a lower bound; `imaging.bridge.worklist` has no single total order (groups appended; declared key `group`, tie-break `itemRef`); `rcm.claims.worklist` `totalCount` is page-size (superseded by B11 queues).
