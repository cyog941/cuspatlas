## I1 private object storage boundary

Design (storage boundary record; the plan asks for an ADR, but the only reserved imaging ADR identity is 0004 for the bridge boundary, so the record lives here until a number is reserved in [ADR-REGISTRY](../ADR-REGISTRY.md)):

- Port `ObjectStorePort` (`packages/contracts/src/imaging.ts`): `stage`, `readStaged`, `promote`, `quarantineStaged`, `quarantineStored`, `discardStaged`, `read`, `head`, `putContent`, `remove`, `writeTombstone`, `hasTombstone`. Every method takes the server-derived tenant; the adapter builds every key itself (`staging/<tenant>/<uuid>`, `t/<tenant>/sha256/<aa>/<digest>`, `quarantine/<tenant>/<id>`, `tombstones/<tenant>/<objectRef>`) and refuses anything else, including another tenant's prefix, as `path_traversal`. No listing and no URL exist on the port; a maintenance listing (`listLocalStoreKeys`) is a separate function never given to request paths.
- Content addressing by SHA-256 inside the tenant prefix: tenants never share bytes. `read` verifies the bytes against the registered digest on every read (the key names the digest and the row's digest must agree too). The database binds `storage_key` to the row's own tenant and digest with a CHECK, so no row can point at another tenant's bytes or at a free path.
- Local adapter (`packages/db/src/object-store-local.ts`): atomic writes (temp file + rename), private file modes, refused under `production` (I-D1 picks the managed backend). Tests use a per-run directory under `os.tmpdir()` removed on teardown.
- Metadata (`cuspatlas.imaging_objects`, `imaging_object_provenance`, `imaging_read_grants`; migration `20261111000000_imaging_objects.sql`): RLS enabled and forced, runtime role SELECT/INSERT, UPDATE only on object state/quarantine reason/version and on grant revocation; triggers make identity, bytes, digest and key immutable, state forward-only (available -> quarantined | deleted, quarantined -> deleted), provenance append-only and written once per ingress, grant revocation one-way by the acting principal; nothing is deleted. The storage key is never returned.
- Read grants (`packages/domain/src/imaging/tokens.ts`): `v1.<grantRef>.<exp>.<HMAC-SHA-256>` over tenant, principal, object, grant and expiry; secret `CUSPATLAS_IMAGING_TOKEN_SECRET` (>= 32 bytes) or the test-only secret under `synthetic-test` (refused elsewhere). Content read order: authentication (live membership), authorization, object visibility (another tenant's object = 404 like a missing one), token (HMAC, expiry, live unrevoked grant row of the same principal; else 403 with attempt reason `object_token_invalid`), state, then verified bytes. Issuing a grant is deliberately not idempotent by key (each call mints a new grant), so no token enters `command_idempotency`.
- Integrity failure: a digest mismatch or missing bytes on read quarantines the object (committed, audited), copies the altered bytes to quarantine for investigation, logs the fixed alert `imaging_object_integrity_failed`, records attempt reason `object_integrity_failed` and refuses 409 `digest_mismatch` / `bytes_missing`; the object is never served again. `imaging.storage.reconcile` (admin.configure) runs the same check over available objects (bounded to 500 per run, `more` flag).
- Store outage or absent store: typed retryable 503 with alert `imaging_object_store_unavailable`; never an empty result.
- Orphan sweep policy: a staged object is never available (I2 separates staging from availability); abandoned staging is swept by the reconcile step added in I2; content bytes without any object row are found by the maintenance listing and are an operator-reviewed removal (not automatic in this batch).

Acceptance cases (`tests/integration/imaging-storage.test.ts`, 15 tests, every denial under the runtime role): adapter content addressing, verification on every read, traversal and foreign-prefix refusal, no listing/URL on the port; production refusal and the secret rule; metadata with digest and provenance and no storage key on REST and MCP; cross-tenant describe, sign and read indistinguishable from missing (identical bodies, attempt `resource_hidden_or_missing`), stolen token still 404; verified bytes with `no-store`, `nosniff`, `attachment`, `no-referrer` headers and a sensitive-read row; token bound to principal (another member's use is 403 `object_token_invalid`), missing/tampered/forged tokens and a signed token naming a non-existent grant refused; expired grant refused; revoked grant refused at once, only its holder (or an `imaging.write` member) may revoke, second revoke 409; actor revoked between grant and read refused (`membership_inactive`) and cannot obtain a new grant; digest mismatch quarantined with bytes retained and alerted, never served again; integrity sweep quarantines missing bytes and does not touch another tenant; no MCP content tool; marker in a filename never reaches logs, audit, outbox, attempts or idempotency, and no image bytes are logged; runtime-role database boundary (immutable digest/key, no delete, foreign-tenant key and traversal key refused by CHECK, foreign tenant by RLS, provenance once, path-like filename refused); absent store is a 503 with an alert.

## I2 ingress pipeline with staging, gating and dedupe

Design:

- Operations (`imaging.ingress.begin|upload|complete` need `imaging.write`; `.read|failures` need `imaging.read`; human or service, a future bridge being a service principal): `POST /v1/imaging/ingress` declares media type, exact length, SHA-256, provenance and optionally the patient the uploader names; `POST /v1/imaging/ingress/{ingressRef}/content` (application/octet-stream, REST only, idempotent by key and byte digest) stages the bytes; `POST .../complete` gates them; `GET .../{ingressRef}` and `GET /v1/imaging/ingress/failures` (exception-first work items: quarantined with the failed gate, held on an undecided scan, incomplete). MCP has begin, complete, read and failures; never the upload.
- Storage (migration `20261111010000_imaging_ingress.sql`): `imaging_ingress_sessions` (declared values and provenance immutable by trigger, forward-only states `awaiting_bytes -> staged -> accepted | quarantined`, `abandoned`; staging and quarantine keys checked to the session's own tenant prefix; RLS forced; runtime UPDATE only on state/observation columns). `imaging_objects.dedupe_patient_id` with a partial unique index (tenant, digest, named patient) `NULLS NOT DISTINCT` over available originals. Both patient columns are listed in `MERGE_EXCLUDED_REFERENCES` (the association decision, I3, is the record that follows a merge).
- Malware gate: `MalwareScannerPort` with `clean | infected | unknown`; no real scanner is qualified (blocked); no scanner configured means every verdict is `unknown`, so nothing ever becomes available. Tests use a synthetic fake that flags a synthetic EICAR-like marker string (deliberately not the real EICAR file).
- Sniffing by magic bytes only: PNG, JPEG, TIFF, PDF and DICOM (`DICM` at offset 128; stored opaquely, no parsing). Unknown magic is `content_type_unrecognized`; a disagreement with the declared type is `content_type_mismatch`. File names never decide anything.
- Abandoned ingress (older than 24 h) is swept by `imaging.storage.reconcile`: staged bytes discarded, session `abandoned`, never an object.
- Crash windows: promotion moves staged bytes to the content key before the database commit; a rolled-back completion leaves verified content bytes without a row (an orphan the maintenance listing finds), and a retry verifies those bytes instead of failing.

Acceptance cases (`tests/integration/imaging-ingress.test.ts`, 15 tests): accepted path with provenance (filename, placeholder device and software, acquisition instant with IANA zone) and verified download; PDF accepted by magic bytes despite a `.png` name; interrupted upload never an object (`bytes_not_received`); MIME spoofing (JPEG bytes declared PNG) and unrecognized bytes quarantined with the file kept in quarantine and attempt reason `upload_gated`; synthetic malware quarantined, never an object, listed in the failure worklist; unknown verdict held `staged` and visible, then accepted once decided; digest mismatch (declared, caller-observed) and truncated upload (`size_mismatch`) never available; oversize refused at begin (with the published limit) and at upload, transport limit refused before the domain; traversal-like names (`../`, backslash, control characters, `..`) and missing or unknown time zones refused; completion idempotent by key, a second key is `duplicate_completion`, re-upload refused; same bytes for one patient dedupe to one object with two provenance rows, for two patients two objects sharing one blob; another tenant cannot upload to, complete or read an ingress or name another tenant's patient; MCP begin/complete parity and no upload tool; abandoned sweep; no marker, malware signature or bytes in logs or audit/outbox/attempt/idempotency rows.

Negative harness: begin, upload (REST only), complete, read and failures rows added (cross-tenant, revoked, downgraded; REST and MCP where a tool exists).

## I3 patient matching, association correction and the imageRef

Design:

- Operations: `imaging.associations.candidates|confirm|correct` (`imaging.associate`, people only), `.history`, `.unmatched` and `imaging.imageRefs.resolve` (`imaging.read`). REST under `/v1/imaging/objects/{objectRef}/match-candidates|association|associations`, `/v1/imaging/associations/{decisionRef}/correct`, `/v1/imaging/worklists/unmatched`, `/v1/imaging/image-refs/{imageRef}`; MCP twins for all of them.
- Matching: an ingress may carry `patientHints` (family/given name, birth date, identifier, phone). They are stored only as tenant-bound HMAC match keys with the S pepper (the same keys S stores for patients), never as text. Candidates: the patient the uploader named (`operator_selected`) and patients sharing an identity key; reasons `same_identifier`, `same_legal_name`, `same_birth_date`, `same_phone`. A phone (household) match alone never qualifies; merged patients are never candidates. Exact = identifier, or legal name and birth date together. Candidates never bind (`autoAssociated: false`); with no metadata the read states the limitation `no_patient_metadata` instead of guessing.
- Decisions (`imaging_match_decisions`, migration `20261111020000_imaging_association.sql`): one current decision per object (partial unique index), basis `operatorSelected | metadataExact | metadataAssisted` (a metadata basis must match the candidate evidence, else 409 `candidate_not_confirmed`), actor and time from context. Confirming while a decision is current is 409 `association_conflict`. Correction requires a reason, supersedes the current decision first and then appends the new one (the database never sees two current decisions), keeps both readable in order, refuses a superseded decision (409 `decision_superseded`), the same patient (422 `same_patient`), another tenant's patient (404) and a merged patient (409 `patient_merged`). Lock order: object, current decision, patient. Only available originals can be associated (`object_not_available`, `derived_not_associable`). The guard trigger allows only supersession once or a merge relink of the patient reference.
- `imageRef` (`imaging_image_refs`, append-only): minted once per object at its first decision and stable afterwards (I-T8). The reference read `imageReference(tx, imageRef, expectedPatientRef?)` (exported for in-process consumers, also REST/MCP) returns object state, media type, length, SHA-256, the current decision, the decision count and `matchesExpected`. This is the seam C15 stores and CL-04 attachment packages bind by hash: a package must refuse when `matchesExpected` is false or the digest differs from the one it recorded.
- Merge (S6): class `imagingAssociation` (`imaging_match_decisions.subject_patient_id`, `factKind: clinical`) registered in `MERGE_RECORD_CLASSES`; the digest excludes the patient reference and supersession bookkeeping. Image bytes and digests live on `imaging_objects` and are never touched by a merge (tested). The two I2 patient columns are explicit exclusions.
- Unmatched worklist: available originals without a current decision, with `ageHours`; escalated after 48 h (I-D8 pending), never discarded.
- Contract deviation (I-T8): the plan's acceptance case "a superseded decision's imageRef stops being current" conflicts with the batch instruction "imageRef stable across corrections". Implemented: stable handle plus an explicit currency check in the reference read. SHARED-CONTRACTS (which wins over plans) only fixes that C stores `imageRef`; recorded for C15/B owner review rather than stopping the batch, because a recommendation exists and the hazard (a consumer silently showing a moved image) is covered by `matchesExpected`.

Acceptance cases (`tests/integration/imaging-association.test.ts`, 8 tests): exact metadata proposes a candidate with reasons but the object stays unassociated (and in the unmatched worklist with its age) until a recorded decision mints the imageRef; a shared phone alone is no candidate, a name-only match is assisted not exact, a basis that overstates the evidence is refused, an operator may decide explicitly, missing metadata is a stated limitation; hint text is never stored (marker absent from every row); correction appends, keeps history, stays one current decision, refuses superseded/same/foreign patients and a missing reason, and the reference read reports `matchesExpected` false for the earlier patient and true for the new one; concurrent confirmations and concurrent corrections each resolve to one current decision with the other a 409; quarantined objects cannot be associated, service principals and imaging writers without `imaging.associate` are refused, another tenant is hidden, confirmation is idempotent by key; MCP parity including the superseded-decision refusal; a merge relinks the decision with equal before/after digests while the object digest, version, bytes and imageRef stay unchanged, and a merged identity cannot receive new associations.

Negative harness: candidates, confirm, correct, history, unmatched and resolve rows.

## I4 mounts, annotations and derived images as separate objects

Design:

- Operations (`imaging.write` for writes, `imaging.read` for reads; human or service): `imaging.mounts.create|revise|read`, `imaging.annotations.create|supersede|list`, `imaging.derived.create`. REST under `/v1/imaging/mounts`, `/v1/imaging/objects/{objectRef}/annotations|derived`, `/v1/imaging/annotations/{annotationRef}/supersede`; MCP twins (no bytes).
- Storage (migration `20261111030000_imaging_composition.sql`): `imaging_mounts` (template fixed, current version pointer moves by one), append-only `imaging_mount_slots` per version (unique slot and object per version), `imaging_annotations` (one row per version of a lineage; one current version; a version is immutable except being marked superseded once; geometry bounded and normalized; label caller text bounded and kept out of audit/outbox), append-only `imaging_derivations` (every attempt, succeeded or failed, with source digest, transform, author). `imaging_objects` gains `source_object_id` and `derivation_key` (fixed at creation; no self foreign key because the logical restore loads a table in one pass) and one available derivation per source and canonical transform.
- Mount rules: slots within the template's count, unique slots and objects; every slot object available and currently associated with the same patient (`invalid_slot` 422, `object_not_available`, `object_unassociated`, `mixed_association` 409, another tenant's object 404); the whole mount is refused in one transaction. Revision requires `expectedVersion` (409 `stale_version`). Reads by version show slot state `present | unavailable | missing` (missing after an I8 deletion) and the current patient.
- I3 coupling: moving an object that is in a current mount version to another patient is 409 `mount_amendment_required` naming the mount (the plan's "study amendment required"; there is no study aggregate in this batch).
- Derived images: decoded and re-encoded by the zero-dependency PNG codec (`packages/domain/src/imaging/png.ts`, bounded dimensions and inflated size); the source is read verified and never written; the result is a new content-addressed object (`kind: derived`) whose read shows its derivation (source, source digest, transform, author, time) and the source's association (`inherited: true`); it cannot be associated, derived again or presented as an original. A transform that cannot run (non-PNG or undecodable source) commits a failed derivation record and refuses 422 `transform_unsupported`; an out-of-bounds crop is 422 `crop_out_of_bounds`.
- Not built here: exported artifacts (so "a mount version referenced by an export cannot be deleted" has nothing to reference yet; mounts are never deleted at all), thumbnails, a viewer, measurements.

Acceptance cases (`tests/integration/imaging-composition.test.ts`, 8 tests): mount revision is a new version with the prior version readable and originals' registered digests and on-disk bytes unchanged; invalid slots, duplicate slots, unknown templates, mixed and missing associations and foreign objects refused with nothing written; correction of a mounted object refused naming the mount; annotation create, supersede and withdraw keep every version readable, invalid geometry refused, the original unchanged and the label absent from every leak surface; annotation on an unavailable object refused; a crop derivation is a new object with its provenance and inherited association, decodes to the cropped size, deduplicates the same transform, rotation and inversion succeed, the derived object cannot be associated or derived again, the source lists it, the original is unchanged; a failed derivation is recorded with the source unchanged and an out-of-bounds crop refused; MCP parity for mount, annotation and derivation.

Negative harness: mount create, revise and read; annotation create, supersede and list; derived create.

## I8 retention, deletion and legal hold

Design (operator procedure and backup interaction in [docs/runbooks/imaging-deletion.md](../runbooks/imaging-deletion.md)):

- Operations: `imaging.retention.setPolicy` (`admin.configure`, people only), `.policies`; `imaging.legalHolds.place|release` (`imaging.legalHold`, people only), `.list`; `imaging.deletions.request|execute` (`imaging.delete`, people only), `.evaluate` (`imaging.read`). REST and MCP.
- Storage (migration `20261111040000_imaging_retention.sql`): append-only `imaging_retention_policies` (versions per record class; `approval_status` can only be `recommended_pending_approval`), `imaging_legal_holds` (released once by the acting person), `imaging_deletion_requests` (one pending per object; identity fixed; executed once; a CHECK enforces the second person when required; byte state settles once), `imaging_objects.deleted_at|deletion_id` with a tombstone CHECK.
- Shared refusal contract extension (same commit): `RefusalDetail.earliestAllowedAt` (date-time) in `context.ts` and the `Refusal` schema, for `minimum_retention_not_met`.
- Evaluation order: active holds (object, its source original, every patient ever associated, merged identities), then the class's latest policy (missing = refused), then minimum retention from receipt. Blocked refusals are `replayable: false` (a hold can be released and time passes, so a same-key retry is evaluated again).
- Execution: re-evaluated, dual approval, one transaction tombstones the object and its derived objects and revokes their grants; then tombstone markers, byte removal (unless another live object shares the blob) and the recorded byte state; retried idempotently by a repeat execute or reconcile. Reconcile also turns a live row with a tombstone back into `deleted` (restore drill).

Acceptance cases (`tests/integration/imaging-retention.test.ts`, 8 tests): no policy means refused (`retention_policy_missing`, attempt row); minimum retention refused with the computed earliest date, a policy change deletes nothing, non-admins cannot set policy; a patient hold blocks the request with the hold as the reason, release allows it, an object hold placed after the request blocks execution with nothing half-deleted, the evaluation shows the rule; an associated image needs a second person, then is tombstoned with metadata, digest and provenance kept, bytes removed, its old grant refused, its derived object deleted, its mount slot shown missing, audit kept, and a replay or a second execute reports the same outcome; a never-associated object is deleted by its requester while identical bytes of another patient's object are retained and still readable; writers, service principals and other tenants are refused or hidden; a simulated restore that lists the deleted object as available is reconciled back to deleted and never served; MCP parity for holds and deletion refusal.
