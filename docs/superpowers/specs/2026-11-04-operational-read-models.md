# Operational read models, work queues and staff context

Date: 2026-11-04. Status: **proposed**. These are user-directed product requirements from a product-pattern review kept outside this repository. No other product's names, screens, code, imagery or visual design are recorded or copied here. Per AGENTS.md these are workflow requirements only. UI design remains deferred. Each requirement below names an owning workstream. Its implementation tasks are in the [operational read models plan](../plans/2026-11-04-operational-read-models.md).

Evidence category for every row: **proposed** (our requirement). Nothing here is an observation of the incumbent or a vendor claim.

## Why

The domain modules record facts correctly but expose them one aggregate at a time. Front-desk, clinical and billing staff need a few composed, honest views that answer the next question without a second lookup. They also need named work queues that turn records into owned work. This extends [practice time and automation](../../PRACTICE-TIME-AND-AUTOMATION.md) (UX-01 to UX-03, PT-01, PT-02, the exception-first rules and the claims loop). The underlying state machines do not change.

## Rules that apply to every requirement

- A read model composes facts owned elsewhere. It never writes, never copies authoritative values into its own tables, and never invents a state. Work queues over a lifecycle are **predicates**, not new lifecycle states.
- Each component of a composed read carries its own authorization outcome. A field the caller may not see is returned as `restricted`, not silently omitted. A producer that does not exist yet is returned as `unavailable` with its owner. Neither of these counts as "none".
- Every list and worklist response carries the shared list envelope in OR-01.
- No colour, layout or component semantics in any API. Contracts expose a semantic category, and visual treatment is a later design decision.

## Requirements

| ID | Requirement | Owner | Acceptance evidence |
|---|---|---|---|
| OR-01 | **List envelope.** Every list or worklist response carries `asOf` (server instant), `appliedFilters` (normalized, including defaults the server applied), `scope` (tenant-wide, assigned locations or explicit location set), `limit`, `truncated`, `nextCursor`, `ordering` (`key`, direction and documented tie-break) and `count` as `{exact}` or `{atLeast}`. An empty result states `count.exact = 0` with the same envelope. | A (shared contract, adopted by every workstream) | A catalog-wide conformance test fails any list operation without the envelope. Tests cover an empty list, a truncated list and a location-restricted caller. |
| OR-02 | **State vocabulary with labels.** Every persisted state code (attendance, appointment, request, claim, payment plan, message, work item and similar) is served from a versioned vocabulary resource as `{code, shortCode, label, category, terminal}`. The label is operator-facing plain language. Category is semantic (`lifecycle`, `presence`, `exception`, `financial`, `clinical`). Responses that carry a code also carry the vocabulary version. | Each owning workstream; the vocabulary endpoint is A | Every code in every state CHECK constraint has exactly one vocabulary entry. A missing label fails CI. Filter sentinels never appear as states. |
| OR-03 | **Schedule view read model.** One query for a location and date range returns the appointments and, for each, the patient summary, coverage verification status, a balance summary, planned procedures with tooth/surface, attendance state with allowed next transitions, type, time, resources and request link. It also returns time blocks as single objects spanning their resources, unavailable intervals with a reason (closed, blocked, outside availability) distinct from free time, and counters with scope (open requests, blocks, staging list, waitlist). A `grain` of `detailed` or `compact` changes only which fields are included. | S (scheduling facts), composed by A (OR-09) | One synthetic day returns every component in one round trip. A caller without `billing` or `clinical` read gets `restricted` components. A missing producer gives `unavailable`. Results agree with S9 search and S10 booking for the same day. |
| OR-04 | **Availability search filters.** S9 already supports duration-only search. Add time-of-day windows, a weekday set, a provider preference, a "next N openings" mode and a configurable maximum window. The default window bound proposal is 60 days, pending S-D/ADR 0009 R3. | S | Tests: duration-only with a weekday set and a morning window; next-3 mode; window above the configured maximum refused with the limit named. |
| OR-05 | **Bounded staging list for appointments being moved.** A per-location list with configurable capacity. An entry references an existing appointment that keeps its booking and occupancy until a new slot is booked or the appointment is explicitly cancelled, or it references an appointment request. Moving an entry to a slot is the S10 reschedule command, atomic. Adding over capacity is a typed refusal naming the capacity. Add, remove and move are each audited. It is not an appointment state and does not weaken occupancy rules. | S | Capacity refusal; move success; move conflict leaves the original booking intact; two staff moving the same entry gives one success and one typed conflict. |
| OR-06 | **Floor and flow view, provider request and team presence.** A read model per operatory gives the current visit (from S11 attendance), elapsed time, plain state label, next action and an open provider-request flag. A command `requestProvider(appointmentRef, reason)` records a request fact for a provider, is acknowledged or cleared by that provider, raises an internal staff notification only, and is never patient-facing. Team presence is a small staff-owned status (available, busy, away, plus optional operatory assignment), self-set, audited and expiring. Shared-display use follows A18's privacy rule: no patient names by default on a display principal. | S (A18 for the shared-display rule) | Synthetic day: arrival → in care → provider requested → acknowledged → checked out. Presence expiry. Display-principal view hides patient identity. |
| OR-07 | **Claims work queues and headline measures.** Named queues as predicates over the B6/B7/B8 lifecycle: `to_create`, `ready_to_submit`, `attachments_needed`, `awaiting_payer`, `rejected_or_denied`, `appeals`, `filing_deadline_soon` (configurable days), `returned`, `paid_closed` and `all`. Each has a count, scope and the OR-01 envelope. Headline measures (open insurer receivable, claims over 30 days, needs action, open appeals) have declared definitions following A16. The default ordering is **work priority**: deadline proximity, then exception severity, then age, with `claimRef` as the documented tie-break. | B | Every claim falls in exactly the queues its predicates select. Measures reconcile to the journal. Ordering is stable and documented in the contract. |
| OR-08 | **Messaging needs-reply queue.** E5 threads get `all`, `unread` and `needs_reply` filters. `needs_reply` has a policy-defined reply-due time per staff queue, escalation when overdue, assignment and counts. The existing awaiting-reply work item becomes this queue's source; no second mechanism is added. | E | A portal message creates one needs-reply item with a due time. A staff reply clears it. Overdue items escalate once. Scope and counts follow OR-01. |
| OR-09 | **Read composition ownership.** A owns read composers: cross-aggregate reads that call each owning domain's published read function inside one tenant transaction. Each component gets its own authorization decision and carries its own freshness and permission state. Composers write nothing. Each composer is a catalog operation with REST and MCP parity. | A | A structural test shows composers import only published domain read functions and issue no writes. A parity test covers the composers. |
| OR-10 | **Appointment detail summary.** A composer returns, for one appointment: patient summary (name, age, practice chart identifier, phone only with contact-read permission), coverage verification status and carrier, balance summary, planned procedures, attendance and next transitions, and a reference for opening the chart. | A, composing S, B, C | One call replaces the per-module reads. Restricted components are labelled. |
| OR-11 | **Reassigning an appointment's patient.** Command `reassignAppointmentPatient(appointmentRef, patientRef, reason)` is allowed only while no clinical, procedure, billing or attendance fact references the appointment. Otherwise it is refused with a typed reason (`clinical_facts_attached`, `charges_attached`, `attendance_recorded`), the blocking refs the caller may see, and the remediation operation (for example procedure review and reversal through C14). It never moves C or B facts, and it is audited. | S (C and B supply the attachment probes) | Allowed case; each refusal case names its remediation; a concurrent C14 render makes the reassignment lose with a typed conflict. |
| OR-12 | **Saved views, favourites and recent patients.** Per-user server-side preferences hold saved list and report views (filters only, no PHI in names) and favourite reports. A per-user recently-opened-patients list holds references only, with short retention, is user-clearable, and is never shared across users or tenants. | A (A16/A17 surfaces) | Cross-user and cross-tenant isolation tests; retention purge; a saved view replays to the same applied filters. |
| OR-13 | **Agent workspace.** Agent sessions have history, scoped memory and scheduled tasks. Memory is tenant-bound, holds no PHI unless an explicit per-tenant policy allows it, has retention and deletion, and every read and write is audited. Scheduled tasks run only under a revocable standing policy rechecked at execution. Everything is a catalog operation through the single authorization path. The default stays read and draft only, per AI-PMS-ARCHITECTURE. | A (A8, A9, A11) | Memory cross-tenant isolation, PHI-policy refusal, deletion, scheduled task refused after policy revocation. |
| OR-14 | **Navigation from the operation catalog.** The A4 catalog exposes navigable capabilities grouped by domain area (scheduling, clinical, financial, communications, imaging, administration), each with the operations it needs. A navigation entry with no backing operation cannot exist. Financial destinations group under one financial area. | A | A test that every navigable capability resolves to registered operations, and that no capability points at a missing route. |

## Deliberately not adopted

- State codes without a plain label (OR-02 requires both).
- Colour or visual meaning in contracts (only semantic category).
- Separate top-level destinations per money concept (OR-14 groups them).
- Hand-maintained navigation (OR-14).
- Any visual treatment. Design stays deferred.
